## 二、问题时间线

### 1. `/dev/video0` 和 `/dev/video1` 能否同时保留

可以，但前提是它们代表两个独立采集设备，而不是同一摄像头暴露的不同功能节点。

先确认设备身份和能力：

```bash
v4l2-ctl --list-devices
v4l2-ctl -d /dev/video0 --all
v4l2-ctl -d /dev/video1 --all
v4l2-ctl -d /dev/video1 --list-formats-ext
```

使用原则：

- 一个 `/dev/videoX` 同一时刻只能被一个采集程序占用。
- 若两路都在同一个 USB Hub 上，先用 `640x480@30` 验证带宽；双路 MJPEG 一般比双路 YUYV 更省 USB 带宽。
- `/dev/video0` 已由 ROS2 相机节点使用时，测试第二路应选择经确认的 `/dev/video1`，不能两个程序抢读 `/dev/video0`。

### 2. GStreamer 报 `WARNING: erroneous pipeline: syntax error`

**原因**：反斜杠 `\` 被放进同一行管线中。它只用于 shell 的“换行续写”，不能作为管线中的独立符号。

正确的单行 MJPEG 预览命令：

```bash
gst-launch-1.0 -v v4l2src device=/dev/video0 io-mode=mmap ! 'image/jpeg,width=640,height=480,framerate=30/1' ! jpegparse ! jpegdec ! videoconvert ! autovideosink
```

若分行书写，反斜杠必须位于每行最后，且后面不能有空格：

```bash
gst-launch-1.0 -v v4l2src device=/dev/video0 io-mode=mmap ! \
'image/jpeg,width=640,height=480,framerate=30/1' ! \
jpegparse ! jpegdec ! videoconvert ! autovideosink
```

运行前须确保 ROS2 的 `v4l2_camera_node` 没有占用同一个节点。

### 3. GStreamer 报 `not-negotiated`

**当时判断**：这不是语法错误，而是 `/dev/video0` 未能以 MJPEG 模式成功启动；最优先排查设备是否仍被 `v4l2_camera_node`（记录中 PID 为 `7013`）占用。

排查顺序：

```bash
kill 7013
sleep 1
sudo fuser -v /dev/video0
```

最后一条没有输出才代表设备已释放。随后先绕过 GStreamer，用 V4L2 验证格式本身：

```bash
v4l2-ctl -d /dev/video0 \
  --set-fmt-video=width=640,height=480,pixelformat=MJPG \
  --set-parm=30 \
  --stream-mmap=3 \
  --stream-count=30 \
  --stream-to=/dev/null
```

只有该命令成功后，才继续测试 MJPEG 的 GStreamer 管线。若不停止 `/dev/video0` 上的 ROS2 节点，则应改测确认可用的 `/dev/video1`。

### 4. `The pixelformat 'MJPG' is invalid`

**现象含义**：`v4l2-ctl` 没有真正把设备切换到 MJPG。`Frame rate set to 1000/29.97 fps` 只是实际帧率约为 30 FPS；短时测试里的 `dropped buffers: 1` 不是主故障。

**建议的降级验证**：先用相机同样支持的原始格式 `YUYV`，确认摄像头、USB 和设备节点可工作。

```bash
v4l2-ctl -d /dev/video0 \
  --set-fmt-video=width=640,height=480,pixelformat=YUYV \
  --set-parm=30 \
  --stream-mmap=3 \
  --stream-count=60 \
  --stream-to=/dev/null

gst-launch-1.0 -v v4l2src device=/dev/video0 io-mode=mmap ! \
'video/x-raw,format=YUY2,width=640,height=480,framerate=30/1' ! \
videoconvert ! autovideosink
```

注意格式名：V4L2 写 `YUYV`，GStreamer caps 写 `YUY2`。

### 5. ROS2 报 `Unrecognized image encoding []`

**已定位原因**：摄像头实际输出 MJPG，但该机上的 ROS2 `v4l2_camera` 无法处理 MJPG；源图像的编码因此为空，后续 `cv_bridge` 转 `rgb8` 时失败。

关键日志：

```text
Current pixel format is not supported yet: MJPG
Unrecognized image encoding []
```

**解决方式（已成功）**：将 ROS2 相机节点固定为 YUYV 输入、RGB 输出：

```bash
ros2 run v4l2_camera v4l2_camera_node --ros-args \
  -p video_device:=/dev/video0 \
  -p pixel_format:=YUYV \
  -p output_encoding:=rgb8 \
  -r image_raw:=/image_raw \
  -r camera_info:=/camera_info
```

`Permission denied` 的摄像头控制项警告当时被判断为非致命，不是这次崩溃原因。

### 6. 启动相机后仍有大量日志

以下日志表示相机已成功启动：

```text
Requesting format: 640x480 YUYV
Successfully set format
Starting camera
```

其余信息的解释：

| 日志 | 影响 | 处理 |
| --- | --- | --- |
| `Permission denied` | 某些摄像头控制项不可读取 | 测试取图阶段可先忽略 |
| `Unable to open camera calibration file` | 缺少标定文件 | 视频预览可用；SfM 正式采集前必须标定 |
| `yuv422_yuy2 => rgb8` | 正在执行颜色格式转换 | 是性能提示而非失败；640×480 测试可接受 |
| `sudo: ros2: command not found` | `sudo` 环境没有加载 ROS2 | 不要用 `sudo ros2 ...` 启动节点 |

保持节点运行，另开终端验证：

```bash
source /opt/ros/humble/setup.bash
ros2 topic hz /image_raw
ros2 topic echo /image_raw --once --field encoding
```

预期：持续输出频率，编码为 `rgb8`。

### 7. YUYV 预览出现黑白画面

**结论**：正常的 `YUYV -> rgb8` 应为彩色；黑白不是预期现象。启动日志成功、控制项权限警告和缺少标定文件都不能解释黑白。

应按以下路径区分问题所在：

1. 保持 ROS2 节点运行，确认发布编码：

   ```bash
   source /opt/ros/humble/setup.bash
   ros2 topic echo /image_raw --once --field encoding
   ros2 run image_tools showimage --ros-args -r image:=/image_raw
   ```

2. 若仍黑白，停止 ROS2 相机节点，直接查看 YUYV 原始画面：

   ```bash
   gst-launch-1.0 -v v4l2src device=/dev/video0 ! video/x-raw,format=YUY2,width=640,height=480,framerate=30/1 ! videoconvert ! autovideosink
   ```

3. 判断：

   - GStreamer 为彩色：摄像头本身正常，问题位于 ROS2 的颜色转换或 ROS 预览链路。
   - GStreamer 仍黑白：YUYV 模式没有正确输出色度；再在设备空闲时测试 MJPEG 原始预览。

对话后续确认“已经成功配置，使用 YUYV”，因此当前应视为相机取图与颜色链路已恢复，继续进行推流而不是重复处理上述旧错误。

## 三、下一步：无人机 4 纯视频推流

### 1. 先确认 Windows 服务可达

保持 `v4l2_camera_node` 运行，在 Jetson 新开终端执行：

```bash
ping -c 4 192.168.30.30
nc -vz -w 3 192.168.30.30 8554
nc -vz -w 3 192.168.30.30 8080
```

Windows 主机需要已启动后端和 MediaMTX。端口含义按历史对话为：`8554` 是媒体服务，`8080` 是后端服务。

### 2. 使用已确定的参数启动纯视频推流

```bash
source /opt/ros/humble/setup.bash
source /home/jetson1/swarm_ws/install/setup.bash

python3 /home/jetson1/jetson1/jetson_video_stream.py \
  --drone-id 4 \
  --backend-drone-id 4 \
  --jetson-ip 192.168.30.103 \
  --mediamtx-host 192.168.30.30 \
  --backend-base-url http://192.168.30.30:8080 \
  --fps 25 \
  --bitrate 2000000 \
  --keyframe-interval 25 \
  --rtsp-transport tcp \
  --no-upload-metadata \
  --no-update-backend
```

### 3. Windows 浏览器验收

打开：

```text
http://192.168.30.30:8889/drone-4
```

连续播放稳定后，才接入 UE 面板。

## 四、SfM 与元数据上传的启用顺序

不要和纯视频推流同时排查。推荐顺序：

1. 先完成浏览器视频稳定播放。
2. 再接入 UE 面板并确认显示稳定。
3. 标定相机，确保 `/camera_info` 中的内参不为 `0`。
4. 确认 PX4 的 `/fmu/out/vehicle_odometry` 持续输出。
5. 最后从推流命令中移除 `--no-upload-metadata` 与 `--no-update-backend`，启用每帧元数据上传。

## 五、后续排障时最重要的规则

- 先确认“设备是否被占用”，再讨论格式、解码器或网络。
- 先用 V4L2/GStreamer 验证摄像头原始画面，再判断 ROS2 或 UE 是否有问题。
- 当前 ROS2 默认方案应为 `YUYV -> rgb8`；MJPG 仅作为摄像头原始预览或后续单独的 GStreamer 推流方案验证。
- 发现黑白、无画面等现象时，分别记录 ROS 预览与 GStreamer 原始预览结果，避免混淆摄像头、ROS 转换、推流和 UE 显示四个环节。
