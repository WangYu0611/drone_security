# 新机载电脑从零配置操作手册（Jetson Orin NX）

本文用于给一架新无人机上的 Jetson Orin NX 配置与旧机相同的环境，最终完成：

- 摄像头在 Jetson 上稳定采集；
- ROS 2 中存在并持续发布 /image_raw；
- PX4 遥测话题可见；
- Jetson 通过 RTSP 向 Windows 的 MediaMTX 推流；
- UE 可通过 MediaMTX 的 WebRTC 页面播放视频；
- 后续可启用每帧图像与 SfM 元数据上传。

> 当前新机的问题是：摄像头已接上，但 ROS 中没有 /image_raw。请严格按本文顺序执行：先确认硬件和图像话题，后测试推流。

---

## 0. 先填写本机参数

以下是当前局域网的实际示例。新飞机必须使用与旧飞机不同的 IP 和 DroneId。

| 项目 | 示例值 | 说明 |
| --- | --- | --- |
| Windows（UE / 后端 / MediaMTX）IP | 192.168.30.111 | 本文所有服务端地址 |
| 旧飞机 Jetson IP | 192.168.30.101 | 仅供参考，不要复用 |
| 新飞机 Jetson IP | 192.168.30.104 | 本次第二架无人机的实际地址 |
| 新飞机 DroneId | 2 | 必须与后台登记一致 |
| MediaMTX 推流路径 | drone-1 | 本次新机的视频路径，独立于后端 DroneId |
| RTSP 推流地址 | rtsp://192.168.30.111:8554/drone-1 | Jetson 向此地址推流 |
| UE/WebRTC 播放地址 | http://192.168.30.111:8889/drone-1 | 浏览器和 UE WebBrowser 使用 |
| 后端地址 | http://192.168.30.111:8080 | video_url、元数据上传 |

先在新机上记录分配结果：

~~~bash
echo "DroneId=2, Jetson=192.168.30.104, Windows=192.168.30.111, Path=drone-1"
~~~

## 1. 安全与基础检查

1. 调试时拆下螺旋桨，或确保无人机不会解锁。
2. 接通 Jetson、电源、摄像头和飞控。
3. 在 Jetson 终端执行：

~~~bash
uname -a
cat /etc/os-release
cat /etc/nv_tegra_release
~~~

确认这是 Jetson Orin NX，并记录 JetPack/L4T 版本。新机应尽量与旧机保持相同 JetPack、Ubuntu 与 ROS 版本。

检查网络：

~~~bash
nmcli device status
ip -4 addr
ip route
ping -c 4 192.168.30.111
nc -vz -w 3 192.168.30.111 8554
nc -vz -w 3 192.168.30.111 8080
~~~

应能看到新机位于 192.168.30.0/24 网段，例如：

~~~text
inet 192.168.30.104/24
~~~

上述 ping 与两个 nc 命令都应成功。若失败，先解决网络，不要启动视频脚本。

若使用 Wi-Fi，关闭省电模式。网卡名以 ip -4 addr 的实际输出为准：

~~~bash
sudo iw dev wlp1p1s0 set power_save off
~~~

## 2. 配置 ROS 2 与 PX4 工作区

每个新终端先加载环境：

~~~bash
source /opt/ros/humble/setup.bash
source /home/jetson1/swarm_ws/install/setup.bash
ros2 --help
ros2 pkg list | grep -x px4_msgs
ros2 topic list
~~~

如果 /home/jetson1/swarm_ws 不存在，先从已经可以工作的旧机复制同一份工作区，或按团队约定重新获取源码再构建。不要自行混用不同版本的 px4_msgs。

工作区源码齐全时：

~~~bash
cd /home/jetson1/swarm_ws
colcon build --symlink-install
source install/setup.bash
~~~

启动与旧机相同的 PX4 Micro XRCE-DDS Agent/桥接程序后，确认：

~~~bash
ros2 topic list | grep '^/fmu/'
ros2 topic hz /fmu/out/vehicle_odometry
ros2 topic hz /fmu/out/vehicle_global_position
ros2 topic echo /fmu/out/vehicle_status_v1 --once
~~~

室内没有 GPS 时，全局经纬度无效是正常的；这不应阻止视频推流。

## 3. 安装视频依赖

在 Jetson 执行：

~~~bash
sudo apt update
sudo apt install -y v4l-utils gstreamer1.0-tools gstreamer1.0-plugins-base gstreamer1.0-plugins-good gstreamer1.0-plugins-bad gstreamer1.0-plugins-ugly gstreamer1.0-rtsp python3-gi gir1.2-gstreamer-1.0
~~~

检查关键组件：

~~~bash
gst-inspect-1.0 nvv4l2h264enc
gst-inspect-1.0 rtspclientsink
gst-inspect-1.0 nvarguscamerasrc
~~~

说明：

- nvv4l2h264enc：Orin 的硬件 H.264 编码器；
- rtspclientsink：向 MediaMTX 推送 RTSP；
- nvarguscamerasrc：仅用于 CSI 摄像头；USB 摄像头不一定需要它。

## 4. 关键关卡：摄像头已接入，但没有 /image_raw

将问题拆分成三层：

1. Jetson 是否识别到摄像头硬件；
2. 摄像头是否能在 Jetson 本地输出画面；
3. 是否有 ROS 2 节点将画面发布为 /image_raw。

### 4.1 USB 摄像头检查

若为 USB 摄像头，执行：

~~~bash
lsusb
ls -l /dev/video*
v4l2-ctl --list-devices
~~~

应至少出现一个 /dev/videoX。假设设备是 /dev/video0，查看支持的格式和分辨率：

~~~bash
v4l2-ctl -d /dev/video0 --list-formats-ext
~~~

用上一步显示的实际格式、宽高进行本地采集测试。例如设备支持 640x480 和 MJPG 时：

~~~bash
v4l2-ctl -d /dev/video0 --set-fmt-video=width=640,height=480,pixelformat=MJPG --stream-mmap=3 --stream-count=100 --stream-to=/dev/null
~~~

没有报错且能正常结束，才说明 USB 摄像头、线缆和 V4L2 基本正常。

### 4.2 CSI 摄像头检查

CSI 摄像头不一定会出现 /dev/video0。执行：

~~~bash
gst-inspect-1.0 nvarguscamerasrc
gst-launch-1.0 -v nvarguscamerasrc sensor-id=0 ! 'video/x-raw(memory:NVMM),width=1280,height=720,framerate=30/1,format=NV12' ! fakesink
~~~

若失败，优先检查：

- CSI 排线方向、插紧情况和摄像头供电；
- sensor-id 是否应为 1；
- 实际摄像头支持的分辨率；
- JetPack 是否有该摄像头的驱动/设备树支持。

### 4.3 检查 ROS 图像话题与发布者

加载 ROS 环境后：

~~~bash
ros2 node list
ros2 topic list -t | grep -E 'image|camera'
ros2 topic info /image_raw -v
ros2 topic info /camera_info -v
~~~

| 现象 | 结论 | 下一步 |
| --- | --- | --- |
| 无 /dev/video，CSI 测试也失败 | Jetson 尚未识别硬件 | 回到 4.1 或 4.2 |
| 本地 V4L2/CSI 测试成功，但无 /image_raw | 缺少 ROS 相机驱动节点 | 启动旧机同款驱动，或参考 4.4 |
| 有 /image_raw，Publisher count 为 0 | 话题存在但驱动没启动/已退出 | 查看相机节点日志 |
| 有发布者但 topic hz 为 0 | 驱动卡住或格式不匹配 | 检查 device、格式、分辨率 |

最终必须确认：

~~~bash
ros2 topic hz /image_raw
ros2 topic echo /image_raw --once
ros2 topic echo /camera_info --once
~~~

/image_raw 应有持续频率、有效 width/height 和 encoding。

### 4.4 没有专用驱动时的 USB 临时方案

若新机为普通 USB/UVC 摄像头，且团队暂时没有专用 ROS 驱动，可先使用 v4l2_camera 验证话题链路：

~~~bash
sudo apt install -y ros-humble-v4l2-camera
source /opt/ros/humble/setup.bash
ros2 run v4l2_camera v4l2_camera_node --ros-args -p video_device:=/dev/video0 -p pixel_format:=MJPG -p output_encoding:=rgb8 -r image_raw:=/image_raw -r camera_info:=/camera_info
~~~

注意：

- /dev/video0、MJPG 必须替换为 4.1 查到的实际值；
- 同一摄像头只能由一个驱动占用，不能同时启动旧机驱动和 v4l2_camera；
- 正式部署优先使用与旧飞机相同的相机启动脚本或 launch 文件。

### 4.4.1 MJPG 报 Unrecognized image encoding [] 的处理

若节点日志同时出现下列内容：

~~~text
Current pixel format is not supported yet: MJPG
cv_bridge::Exception: Unrecognized image encoding []
~~~

说明当前版本的 v4l2_camera 不能正确处理该摄像头输出的 MJPG。不是摄像头断开，也不是视频推流脚本问题。

若 v4l2-ctl --list-formats-ext 显示摄像头还支持 YUYV，停止当前节点后，改用 YUYV 重启：

~~~bash
ros2 run v4l2_camera v4l2_camera_node --ros-args -p video_device:=/dev/video0 -p pixel_format:=YUYV -p output_encoding:=rgb8 -r image_raw:=/image_raw -r camera_info:=/camera_info
~~~

然后立刻验证：

~~~bash
ros2 topic hz /image_raw
ros2 topic echo /image_raw --once
~~~

只有 /image_raw 能稳定输出后，才能继续视频推流。YUYV 在 640x480 下适合先完成链路验证；正式使用 1080p 时，再换用支持 MJPG 的相机驱动或硬件解码方案。

下列日志在当前阶段通常不是致命错误：

~~~text
Failed getting value for control ... Permission denied
Unable to open camera calibration file ...
Image encoding not the same as requested output, performing possibly slow conversion
~~~

它们分别表示：某个 UVC 控制项不可读、尚未创建相机标定文件、节点正在把 YUYV 转换成 rgb8。只要随后出现 Successfully set format 和 Starting camera，且 /image_raw 有持续频率，节点就是正常运行的。不要关闭这个节点；另开一个终端执行 ros2 topic hz /image_raw 验证。

未找到标定文件会让 CameraInfo 使用默认/空内参：不影响当前视频验证，但正式 SfM 采集前必须完成 4.5 节标定。

当前视频脚本可处理的常见编码：

~~~text
rgb8, bgr8, rgba8, bgra8, mono8, yuyv, yuv422_yuy2
~~~

### 4.5 SfM 额外要求：相机标定

视频播放不依赖标定，但 SfM 需要可靠相机内参：

~~~bash
ros2 topic echo /camera_info --once
~~~

若 K[0] == 0，表示未标定；可继续视频测试，但不能作为正式 SfM 数据采集。

棋盘格标定示例。尺寸必须按实际棋盘修改：

~~~bash
sudo apt install -y ros-humble-camera-calibration
ros2 run camera_calibration cameracalibrator --size 8x6 --square 0.025 image:=/image_raw camera:=/
~~~

## 5. 准备 Windows 端服务

Windows 主机是 192.168.30.111。先确认防火墙允许：

| 服务 | 协议/端口 | 用途 |
| --- | --- | --- |
| MediaMTX RTSP | TCP 8554 | Jetson 推流 |
| MediaMTX RTP/RTCP | UDP 8000、8001 | 仅 RTSP UDP 模式需要 |
| MediaMTX WebRTC 页面 | TCP 8889 | UE WebBrowser/浏览器访问 |
| MediaMTX WebRTC ICE | UDP 8189 | WebRTC 媒体协商 |
| 后端 HTTP | TCP 8080 | video_url、元数据上传 |

以管理员 PowerShell 执行：

~~~powershell
New-NetFirewallRule -DisplayName "Drone MediaMTX RTSP" -Direction Inbound -Action Allow -Protocol TCP -LocalPort 8554
New-NetFirewallRule -DisplayName "Drone Backend HTTP" -Direction Inbound -Action Allow -Protocol TCP -LocalPort 8080
New-NetFirewallRule -DisplayName "Drone MediaMTX WebRTC" -Direction Inbound -Action Allow -Protocol TCP -LocalPort 8889
New-NetFirewallRule -DisplayName "Drone MediaMTX ICE" -Direction Inbound -Action Allow -Protocol UDP -LocalPort 8189
New-NetFirewallRule -DisplayName "Drone MediaMTX RTP" -Direction Inbound -Action Allow -Protocol UDP -LocalPort 8000,8001
~~~

确认 tools/MediaMTX/mediamtx.yml 中有：

~~~yaml
webrtcAdditionalHosts: [192.168.30.111]
~~~

启动后端：

~~~powershell
Set-Location D:\RedAlert\UE5DroneControl
.\Backend\build\Release\DroneBackend.exe .\Backend\config.yaml
~~~

启动 MediaMTX：

~~~powershell
Set-Location D:\RedAlert\UE5DroneControl\tools\MediaMTX
.\mediamtx.exe .\mediamtx.yml
~~~

MediaMTX 启动日志应包含：

~~~text
[RTSP] listener opened on :8554
[WebRTC] listener opened on :8889
~~~

## 7. 第一轮只测视频：不上传后台和元数据

先把变量缩小为：新机图像 -> MediaMTX -> 浏览器。

~~~bash
mkdir -p /home/jetson1/video_test_logs
python3 /home/jetson1/jetson1/jetson_video_stream.py --drone-id 2 --backend-drone-id 2 --stream-path drone-1 --jetson-ip 192.168.30.104 --mediamtx-host 192.168.30.111 --backend-base-url http://192.168.30.111:8080 --fps 25 --bitrate 2000000 --keyframe-interval 25 --rtsp-transport tcp --no-upload-metadata --no-update-backend 2>&1 | tee /home/jetson1/video_test_logs/video_only_$(date +%Y%m%d_%H%M%S).log
~~~

Windows 的 MediaMTX 日志正确时类似：

~~~text
[RTSP] [session ...] is publishing to path 'drone-1'
~~~

再在 Windows 浏览器打开：

~~~text
http://192.168.30.111:8889/drone-1
~~~

首次接入使用 TCP，兼容性更好。若 TCP 稳定但延迟会逐步增大，并且确认局域网质量良好，可改用 UDP 对比：

~~~text
--rtsp-transport udp
~~~

建议先以 2 Mbps、25 fps 验证连续稳定，再逐步提高到 1080p 和目标码率。每次只修改一个参数并观察至少 5 分钟。

## 8. 视频稳定后，再接入后台与 SfM 元数据

前提：

1. 后端已登记 DroneId 2；
2. 后端 video_url 对应 http://192.168.30.111:8889/drone-1；
3. 后端 8080 能从 Jetson 访问；
4. /image_raw、/camera_info、PX4 话题均正常。

将第 7 节命令中的下列两个参数删除：

~~~text
--no-upload-metadata
--no-update-backend
~~~

重新启动脚本。日志中应出现：

~~~text
Backend video_url updated
~~~

元数据上传失败通常是网络或后端端口问题；它不应直接导致 RTSP 推流停止。出现问题时先回到第 7 节的纯视频模式定位。

## 10. 常见问题速查

| 问题 | 首先检查 |
| --- | --- |
| 无 /dev/video | USB 线、供电、lsusb、CSI 驱动/排线 |
| 有摄像头但无 /image_raw | 相机 ROS 驱动/launch 是否启动；ros2 topic info /image_raw -v |
| 有 /image_raw 但脚本不出流 | ros2 topic hz /image_raw、图像 encoding、脚本日志 |
| MediaMTX 显示 no stream is available | Jetson 未成功推到 8554；先执行 nc 测端口 |
| nc 8554 或 8080 超时 | 两端不是同网段、Windows 防火墙未放行、服务未启动 |
| 视频断开或延迟增大 | 降到 2 Mbps/25 fps；关闭 Wi-Fi 省电；改为 --rtsp-transport tcp 比较 |
| CameraInfo reports an uncalibrated camera | 视频可测试；SfM 正式采集前完成相机标定 |
| 室内没有 GPS | 正常；保留 odometry 和时间戳，室外再验证全局坐标 |

> 自启动服务请放到最后。只有在手工连续运行 15 分钟以上、画面稳定且日志无重复重连后，才将相机驱动、PX4 Agent、桥接程序和视频脚本写入 systemd。
